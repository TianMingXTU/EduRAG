## 1. 项目背景

### 1.1 行业背景

近年来，以 ChatGPT 为代表的大语言模型（Large Language Model, LLM）技术迅猛发展，AI 大模型已成为企业数字化升级的核心方向之一。教育行业作为知识密集型领域，天然适合引入 LLM 技术来提升教学效率与服务质量。

然而，通用大模型在企业实际落地中面临两个核心瓶颈：

1. **知识更新滞后**：模型的参数化知识依赖于训练数据的截止时间，无法自动获取最新信息（如最新考纲、教材改版、政策变化等）。
2. **缺乏私有领域知识**：通用大模型未经过企业/机构内部数据的训练，对组织特有的知识体系（如学校课程大纲、学科题库、内部FAQ、公司制度文档等）一无所知。

这两个问题直接导致模型回答"看似合理、实则错误"的**幻觉（Hallucination）**现象，严重制约了 LLM 在教育场景中的实际应用价值。

### 1.2 痛点分析

| 角色        | 痛点                                               | 影响                             |
| ----------- | -------------------------------------------------- | -------------------------------- |
| 学生        | 课后遇到疑难问题，无法随时获得准确解答             | 学习效率低，疑问积累影响后续学习 |
| 教师 / 助教 | 大量重复性答疑工作，挤占教研和备课时间             | 人力资源浪费，响应及时性难以保证 |
| 教务管理    | 缺乏统一的知识沉淀与复用机制，FAQ 散落在各个渠道   | 知识资产流失，新教师上手成本高   |
| IT 部门     | 需要一套可落地、可扩展、可维护的企业级智能问答方案 | 试错成本高，技术选型风险大       |

### 1.3 解决思路

本项目采用 **RAG（Retrieval-Augmented Generation，检索增强生成）** 技术路线，结合传统 **FQA（Frequently Question Answering，高频问答）** 系统，构建一套"先查后答、多层兜底"的学科在线答疑系统 — **EduRAG**。

核心设计理念：

- **FQA 层**：对高频、明确的问题，通过 MySQL + BM25 快速命中并返回标准答案，响应快、成本低。
- **RAG 层**：对模糊、复杂、未见过的开放问题，通过向量检索从本地知识文档中召回相关片段，再由 LLM 总结生成答案。
- **融合兜底**：FQA 无法覆盖时自动降级到 RAG，RAG 也无法回答时引导至人工服务。

## 2. 项目目标

### 2.1 业务目标

1. **提升答疑效率**：实现 7×24 小时自动答疑，将常见问题的平均响应时间从人工的分钟级降低到秒级。
2. **降低人力成本**：减少教师/助教在重复性答疑上的投入，预计覆盖 80% 以上的常见问题。
3. **知识资产沉淀**：将散落的 FAQ 和教学文档整合为结构化的企业知识库，实现知识的持续积累与复用。
4. **可复用方案输出**：形成一套标准化的企业级 RAG 实施方案，可快速迁移至其他学科/行业。

### 2.2 技术目标

1. **阶段一（教材实现）**：严格按照教材 Day01-10 的技术路线，完整实现 FQA + RAG 融合系统，确保所有模块可运行、可测试、可部署。
2. **阶段二（升级优化）**：在阶段一的基础上，从检索质量、模型能力、工程性能、用户体验四个维度进行系统性升级，打造生产级 AI 问答产品。

### 4.3 数据流说明

**用户提问 → 系统回答的完整链路：**

1. 用户通过 API 提交问题（query）。
2. **集成路由**首先判断 query 合法性，然后调用 FQA 子系统。
3. **FQA 子系统**：
   - 对 query 做 jieba 分词。
   - 使用预构建的 BM25 索引计算 query 与库中问题的相似度。
   - 若 BM25 分数 ≥ 第一阈值（如 10.0），直接命中。从 Redis 缓存读取答案并返回；若缓存未命中，回查 MySQL 后写入 Redis。
   - 若 BM25 分数在第一阈值和第二阈值之间（如 [0.85, 10.0)），进入 RAG 子系统。
   - 若 BM25 分数低于第二阈值（如 0.85），视为无法回答，引导至人工。
4. **RAG 子系统**：
   - **意图分类**：BERT 模型判断 query 是"通用知识"还是"专业咨询"。
     - 通用知识 → 直接调用 LLM 回答（不检索）。
     - 专业咨询 → 进入检索策略选择。
   - **策略选择**：LLM 分析 query，从四种策略中选择一种：
     - 直接检索（Direct Retrieval）
     - 假设文档检索（HyDE）
     - 子查询分解（Sub-query）
     - 回溯检索（Backtrack）
   - **查询优化**：LLM 根据选择的策略优化 query。
   - **向量检索**：用 bge-m3 将优化后的 query 向量化，从 Milvus 中检索 top-k 相似文档片段。
   - **答案生成**：将 query + 检索上下文 + 对话历史拼入 Prompt，调用 LLM 生成最终答案。
5. 最终答案返回给用户。

### 5.3 MySQL FQA 问答系统

**目标**：实现基于 MySQL + BM25 + Redis 的 FQA 问答子系统，能够对高频、明确的问题实现快速命中并返回标准答案。

**整体工作流**：

```
离线阶段: FQA数据 → MySQL → BM25索引构建(含jieba分词)
在线阶段: 用户query → jieba分词 → BM25检索 → 阈值判断
  ├─ ≥阈值 → Redis/MySQL 读取答案 → 返回
  └─ <阈值 → 转RAG系统 或 返回无答案
```

### 6.1 检索能力增强

#### 6.1.1 混合检索（Hybrid Search）

**问题**：当前系统仅使用稠密向量（dense embedding）进行检索，无法有效处理：

- 精确关键词匹配（如专有名词"Python 3.12"、代码片段）
- 缩写/同义词的精确匹配
- 短文本检索时稠密向量效果不佳

**方案**：实现稠密向量（Dense）+ 稀疏向量（Sparse/BM25）的混合检索。

| 任务编号 | 任务描述                      | 详细说明                                                                                                                                                                              |
| -------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T2.1.1   | 启用 bge-m3 稀疏向量          | bge-m3 模型原生支持同时输出稠密向量和稀疏向量（lexical weight）。修改 EmbeddingModel 的 encode 方法，返回 (dense_vec, sparse_vec) 元组。                                              |
| T2.1.2   | 修改 VectorStore 支持混合检索 | 在 Milvus 中创建 collection 时同时支持 dense 和 sparse 字段。search 方法增加 hybrid_search 参数，使用 Milvus 的 hybrid search API（加权融合两个检索结果，权重比可通过 config 配置）。 |
| T2.1.3   | 混合检索效果对比              | 准备测试集对比三种模式（纯Dense / 纯Sparse / Hybrid）的 Recall@k、Precision@k 指标，选择最优权重配比。                                                                                |

#### 6.1.2 重排序（Reranking）

**问题**：向量检索的 top-k 结果中，前几个结果不一定是最相关的。

**方案**：引入 Cross-encoder 对向量检索结果进行精排。

| 任务编号 | 任务描述                    | 详细说明                                                                                                                                                                                                                                          |
| -------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T2.1.4   | 集成 Cross-encoder Reranker | 在 `rag_qa/core/reranker.py` 中实现 `Reranker` 类。使用 `BAAI/bge-reranker-v2-m3` 或 `cross-encoder/ms-marco-MiniLM-L-6-v2` 模型。`rerank(query, documents, top_k=5)` — 对 query 和每个文档拼接编码，计算相关性分数，按分数降序重排并返回 top_k。 |
| T2.1.5   | 集成到 RAG 流程             | 修改 RAGSystem 的 generate_answer 方法，在 VectorStore.search 之后、Prompt 组装之前，插入 Reranker 步骤：将检索到的 candidate 文档（如 top_k=20）交给 Reranker 精排，取重排后的 top_k=5 用于生成答案。                                            |

## 8. 风险评估与应对措施

| 风险类别 | 风险描述                                 | 概率 | 影响 | 应对措施                                                                                             |
| -------- | ---------------------------------------- | ---- | ---- | ---------------------------------------------------------------------------------------------------- |
| 技术风险 | Ollama 在 CPU 上推理速度慢，影响用户体验 | 高   | 中   | 1) 使用 qwen3:4b 小模型；2) 响应中添加"生成中"提示；3) 可选接入云端 API 加速                         |
| 技术风险 | bge-m3 模型加载占用内存过高              | 中   | 高   | 1) 使用 CPU 推理（速度换内存）；2) 考虑使用更轻量模型如 BAAI/bge-small-zh；3) 模型加载时启用内存映射 |
| 集成风险 | Milvus 服务连接不稳定，影响 RAG 可用性   | 低   | 高   | 1) 实现连接重试机制；2) 增加熔断降级（Milvus 不可用时降级到纯 FQA）；3) 日志告警                     |
| 质量风险 | 检索质量不达标，召回片段与问题无关       | 中   | 中   | 1) 通过 RAGAS 评估量化问题；2) 调优 chunk 大小/重叠/检索策略；3) 引入重排序                          |
| 进度风险 | 阶段一任务量大，模块间依赖复杂           | 中   | 低   | 1) 采用增量开发、持续集成；2) 每个子模块有独立入口可单独测试；3) 按依赖关系有序推进                  |
